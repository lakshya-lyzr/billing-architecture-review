What “billing-only” means here

Products / shared SDKUsage facts, operation/component IDs
PagosAuthoritative wallet, reservations, quotes, provider ledger, durable billing outbox
Billing adapter → Autumn: price-only plans, subscriptions, previews, credit notes
Billing adapter → Stripe: idempotent subscription-scoped final overage items
Stripe Billing: consolidated invoices, collection and recovery → verified paid/refund inbox → Pagos grants/clawbacks

All paid plans had prices and empty items arrays. A deliberate empty default plan prevented the existing test organization’s older auto-enabled credit plan from provisioning credits. A clean deployment should enforce a billing-only catalog and default policy.

Do not bill consumption twice: a paid top-up grants credits in Pagos; normal funded consumption only reduces that wallet. Send only explicitly billable excess or separate fees to the invoice adapter. Scope pending invoice items to the Stripe subscription so an immediate top-up cannot collect the wrong period’s overage.

Keep price ownership clear: product teams approve prices; Pagos freezes usage quotes and calculates the final charge. Native customer base-price overrides customize subscription billing, not the authoritative Pagos wallet.

Remaining qualification

  • The Pagos ledger/inbox is a SQLite validation fixture, not a production wallet, SDK, expiration policy or atomic reservation implementation. Selected-source report balances are illustrative accounting samples, not current spendable balances after monthly expiry.
  • This test intentionally makes no Autumn balance/check/track/reservation API calls and configures no Autumn credit allowances. It does not establish a dependency-minimized deployment: balance worker, Kafka, cache roles, DynamoDB-compatible checkpoints, queues and scheduler remain in the tested stack.
  • The original organization had an older auto-enabled credit plan. The contaminated preliminary fixtures were excluded; current customers explicitly select an empty default plan. Production should use a clean billing-only organization/catalog or enforce this configuration.
  • Overages were computed by Pagos fixtures and delivered as idempotent, subscription-scoped Stripe invoice items. This is an integration we maintain, not native Autumn usage aggregation. General commitment true-ups, tax treatment and cross-product allocation are not qualified.
  • Carrying late usage to the next invoice was validated as a technical behavior; the finance cutoff/correction policy still needs approval before launch.
  • Stripe automatic payment retry was observed; production retry cadence, cancellation/grace policies, email templates/reminders and actual email delivery were not qualified. No email-delivery claim is made; credit-note send_email was false.
  • Checkout, setup and portal URLs were created; 3DS remained unpaid/requires_action. Full browser checkout/challenge completion was not rerun in this billing-only suite.
  • Tax/PO/UPI, arbitrary annual commitments, production load, multi-node failover, coordinated restore, real Pagos integration and migration/cutover remain outside this local qualification.
  • The local stack uses emulated queue/timer/checkpoint services; success does not establish durable production replacements. The pre-existing whole-schema validator issue from earlier investigations is not resolved by this billing suite.
  • Existing additive schema/SQL changes from earlier reservation testing remain in the shared local database, but this run used the original unpatched application image with zero entitlement rows for the billing-only cohort. No reservation path was used.
Do not treat the fixture as a wallet implementation. The reported 19/5 credit samples use selected invoice sources to test deduplication and organization isolation. They do not compute current availability after all monthly expirations, nor implement production reservations or atomic settlement.
